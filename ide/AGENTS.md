# 这个项目怎么写代码

给 AI 看的。下面每一条都是这个仓库里已经在执行的规矩，从现有代码和测试里提炼出来的，
不是新发明的要求。

## 一、先读真代码，再下结论

源码 > 配置 > 文档。`.md` 会过期，`package.json` / `Cargo.toml` 只描述依赖不描述实现。

- 下"这个项目是怎么做的"这类结论前，必须读过相关源文件，不能只看文档和清单。
- 改一个已存在的文件前，必须先拿到它当前的真实内容。
- 找到了更多相关文件就接着读完再下结论，不要停下来问"要不要继续读"。

## 二、没做的事不许报成做了

这是这个仓库栽过最多次的地方，整套测试里有一大半在钉它。

- 退出码就是结论。命令失败就说失败，不要把原始输出原样丢回去当成功。
- 检索类结果要分清"没找到"和"根本没去找"——这两件事不能用同一句话表达。
- 动作没发生就不许报成功。
- 拿不准的结论要标明是低置信、待核实，不要用肯定语气写出来。

## 三、注释写"为什么"和"事故长什么样"

不写"这个函数做什么"（代码本身就说了），写：

- 为什么是这个值、这个顺序、这个边界；
- 改成别的写法会出什么事（最好带实测数据）；
- 这段代码是被哪个真实 bug 逼出来的，那个 bug 的**形状**是什么。

中文讲事故和取舍，英文讲设计和契约，两者混排是这个仓库的既有风格，不用统一。

## 四、测试钉"连接"，不钉"实现"

这个仓库出过的严重缺陷几乎都是同一个形状：**代码存在，但没有任何东西调用它**。类型检查
抓不到，测试也抓不到——它读起来完全像能用的软件。

所以：

- 断言"X 能从 Y 到达"，不要断言"X 是这么写的"。后者会被正常重构搞红，然后被删掉。
- 宁可漏报也不要误报。会叫的狼来了的检查最后一定会被删，删掉之后它什么都不保护。
- 每条守卫要在注释里写清它能抓住的**那个真实缺陷**。
- 源码文本断言必须先剥注释再断言。注释里经常逐字引用被修掉的旧代码，不剥的话
  "旧写法不该出现"这类断言永远是绿的，真改回去了也照样绿。

**新加的守卫必须做变异验证**：把它要防的那个 bug 手动放回去，确认它真的变红，再还原。
没验证过会红的守卫等于没有。

## 五、面向用户的能力做成配置，不要硬编码

用户填一段声明就多一个能力，删掉那段就没了——不改代码、不发版、不重启。

上下文预算是真金白银：没有配置内容时一个字节都不占，不能让空配置每轮白付钱。

## 六、改动要落到源码树

- 只把文件拷进运行环境（`docker cp` 之类）而不改源码树，下次重建就会静默回滚，且不报错。
- 手工构建的二进制迟早会和源码脱节。安全相关的闸要放在构建期，不要依赖手工产物。

## 七、动手前后

- 跑 `npm test`（全量，约 1500 条）。
- 改了 Rust 侧跑 `cargo check`。
- 改了官网跑一次 `website/` 的构建——它有一步会从 `src/main.js` 里抽真实工具目录，
  main.js 动了这一步会先炸。
