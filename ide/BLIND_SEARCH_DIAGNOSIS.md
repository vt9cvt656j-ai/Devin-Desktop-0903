# "闭眼反复搜不存在文件" 问题诊断报告

> 诊断日期: 2026-07-30  
> 目标文件: `src/main.js` (56547 行)  
> 性质: 只读诊断，不改代码

---

## 一、问题定义

用户实证：AI 在已知项目目录里没有某文件时，仍反复搜/读那个不存在的路径，且每次都搜同样的假路径（"固定"）。

这是"证据不足就行动"的变体——模型在幻觉路径上反复投入 token，不吸取失败教训。

---

## 二、调查清单与发现

### 2.1 搜索/读失败是否被记住？

**结论：部分记住，但关键缺口在 read_file 和 find_files 的失败路径上。**

| 机制 | 覆盖范围 | 是否记录失败路径 | 代码位置 |
|------|----------|-----------------|----------|
| `_failedSearchQ` | `search` / `websearch` 工具 | **是**——记录失败的搜索词，模糊去重防重搜 | L37127-37145 |
| `_failedCmdLog` | `cmd` / 终端命令 | **是**——记录失败命令，短路防重跑 | L28590-28620 |
| `_dupReadN` | `read_file` 工具 | **否**——只追踪"已读过的文件被重读"，不追踪"不存在的路径被重试" | L40685-40687 |
| `_pathNotFoundGuided` | `read_file` 工具 | **一次性布尔**——整个 run 只提示一次"请先 list_dir"，之后不再提醒 | L40609-40611 |
| `_toolLedger` | 所有工具 | **记录失败但不记具体路径**——聚合为 `read_file: 3✓/2✗`，丢失了"哪个路径失败"的信息 | L35118-35151 |
| `find_files` 失败 | 文件查找 | **完全没有去重机制**——注释明确说"NOT find_files"（L37125） | L37125 |

**关键缺口**：当 `read_file` 返回 `[ERROR] 找不到唯一文件: xxx` 时：
- 该失败路径 **没有** 被加入任何 "已尝试且失败" 的集合
- 下次再读同一路径时，**没有机制跳过或提示"已搜过"**
- `_pathNotFoundGuided` 只在第一次失败时给一句提示，之后沉默

代码证据（L40589-40613）：
```javascript
if (readFailed) {
  // ... 帮助提示 ...
  let pathGuidance = "";
  if (!run._pathNotFoundGuided) {  // ← 只触发一次
    pathGuidance = "\n\n⚠️ 读不到文件时请先用 list_dir / find_files 确认真实路径...";
    run._pathNotFoundGuided = true;  // ← 之后永远不再提醒
  }
  return { type: "read", path: call.path, content: `[${code}] 找不到唯一文件: ${rawPath}...` };
}
```

对比 `_failedSearchQ`（L37127-37144）——search 工具有完整的失败去重：
```javascript
if (run && _live() && (call.type === "search" || call.type === "websearch")) {
  run._failedSearchQ = run._failedSearchQ || [];
  // ... 模糊匹配已有失败记录 ...
  if (_hit) {
    // 返回 "你之前搜过也没结果" 的拦截消息
  }
}
```

**但 read_file 和 find_files 完全没有对等的失败路径集合。**

### 2.2 AI 为何不吸取教训？

**三个层面的失败信息断裂：**

#### (a) 账本聚合丢失路径信息

`_toolLedgerStats` (L35118-35151) 输出格式为：
```
read_file: 5✓/3✗ (notFound×3；最近失败：找不到唯一文件: src/utils/reverse_engineering_report.md)
```

最近失败原因只保留最后一条的 60 字切片（L35129: `e.reason.slice(0, 60)`），**历史失败路径全部丢失**。模型看到的只是聚合数字，不知道"具体哪 3 个路径失败了"。

#### (b) 主模型上下文中失败证据被稀释

工具失败的结果消息（`[ERROR] 找不到唯一文件: xxx`）确实在对话历史里，但：
- 长对话中早期失败消息被压缩/截断
- 模型每轮重新生成时，幻觉路径可能再次"看起来合理"
- 没有结构化的"这些路径已确认不存在"提示注入到当前轮

#### (c) 失败命令短路不覆盖 read/search 类工具

`_repeatedFailedCmdShortCircuit` (L28615-28620) 只拦截 `cmd` 类型：
```javascript
function _repeatedFailedCmdShortCircuit(run, command) {
  // 只处理终端命令，不处理 read_file / find_files
}
```

调用点 (L44144) 也只在命令执行前：
```javascript
const _repeatFailMsg = _repeatedFailedCmdShortCircuit(run, call.command);
```

**read_file / find_files 没有对等的短路机制。**

---

### 2.3 "固定"搜同一路径的根因

**根因链条：**

1. **模型首次幻觉路径** → 比如 `src/utils/reverse_engineering_report.md`
2. **read_file 失败** → 返回 `[ERROR] 找不到唯一文件`
3. **错误消息进入对话历史** → 但路径本身也被"记住"（在上下文中可见）
4. **后续轮次** → 模型在推理时看到历史中的路径字符串，误以为"可能还没试过"或"可能需要用不同方式读"
5. **没有任何机制说"这个路径已经确认不存在"** → 模型重新发起相同请求
6. **循环重复** → 用户看到"固定"搜同一路径

加剧因素：
- `_pathNotFoundGuided` 只提醒一次（L40609-40611），后续失败静默通过
- `_toolLedger` 的聚合统计不传递"具体哪些路径失败"的信息给主模型
- 对话压缩可能丢失早期的失败证据，但模型对幻觉路径的"记忆"来自其自身的生成倾向

**与 #71（证据分级）、#77（结构摸清）的同源性**：三者都是"模型在证据不足时行动"——
- #71: 不看诊断就下结论
- #77: 不 list_dir 就猜路径
- #78（本问题）: 路径已确认不存在仍反复搜

## 三、修复方向评估

### 方案 A：失败路径短期记忆（事实门控）

**做法**：在 run 上新增 `_failedReadPaths: Set<string>`，read_file / find_files 失败时将路径加入集合；再次请求同路径时直接返回拦截消息。

**优点**：
- 物理阻断，100% 防止同一路径被反复搜
- 与 `_failedSearchQ`（search 去重）和 `_failedCmdLog`（命令短路）哲学一致
- 实现简单，风险低

**缺点**：
- 硬拦截，模型无法"我知道上次失败了但我有理由再试"
- 如果路径确实存在但因为临时权限问题读不到，会被误拦

**贴合度**：中等——属于"事实门控"，但缺少"判断留权"的弹性。

---

### 方案 B：失败证据注入模型上下文（判断留权）

**做法**：在 `_padText()` 或 nudge 机制中，把本轮已失败的路径列表注入到模型可见的上下文中，如：
```
⚠️ 本轮已确认不存在的路径（别再搜）：
- src/utils/reverse_engineering_report.md
- src/components/OldWidget.tsx
请先 list_dir 确认真实结构。
```

**优点**：
- 模型看到证据后自行决定，保留判断权
- 与 `_padText()` 的"运行进度草稿纸"机制天然契合（L36014-36024）
- 不硬拦，模型有理由时可以忽略提示

**缺点**：
- 模型可能仍然忽略提示（"知道但不服"）
- 占用上下文 token（但路径列表通常很短）

**贴合度**：高——完全符合"事实采集、诚实记账、判断留权"哲学。

---

### 方案 C：A + B 结合（推荐）

**做法**：
1. **第一层（软）**：失败路径注入上下文（方案 B），让模型自己看到
2. **第二层（硬）**：同一路径被搜 **第 2 次** 时，返回拦截消息但仍允许第 3 次（给模型"我真的有理由"的机会）
3. **第 3 次以上**：物理阻断，返回"已搜过 3 次，请先 list_dir"

**实现要点**：
- 新增 `run._failedReadPaths: Map<string, number>`（路径 → 失败次数）
- read_file 失败时：`map.set(path, (map.get(path) || 0) + 1)`
- 第 1 次失败：正常返回错误 + 注入上下文
- 第 2 次：返回错误 + 附加"你已搜过此路径，建议 list_dir"
- 第 3 次+：物理拦截，返回"已搜过 N 次，必须先 list_dir 确认真实结构"

**贴合度**：最高——渐进式门控，前两次留判断权，第三次才硬拦。与 `_dupReadN`（重读升级：1次提醒→2次死循环警告）的渐进哲学完全一致（L40681-40687）。

---

## 四、建议

**推荐方案 C（渐进式门控）**，理由：

1. **与现有机制同构**：
   - `_failedSearchQ` 已为 search 做了失败去重（L37127）
   - `_failedCmdLog` 已为 cmd 做了失败短路（L28590）
   - `_dupReadN` 已为重复读做了升级机制（L40685）
   - 方案 C 就是把这三者的哲学统一应用到 read_file / find_files 的失败路径上

2. **判断留权**：前两次失败不硬拦，让模型自己看到证据后决定；只有反复撞墙才物理阻断

3. **实现成本低**：
   - 新增一个 `Map<string, number>` 在 run 上
   - read_file 失败路径 (L40589-40613) 加两行记录
   - read_file 入口 (L40462 附近) 加一个前置检查
   - `_padText()` (L36014) 加一行输出失败路径列表

4. **不影响正常流程**：成功路径不进入集合，零开销；只有失败路径被追踪

---

## 五、风险与注意事项

1. **路径归一化**：`src/foo.ts` 和 `/abs/path/src/foo.ts` 应被视为同一路径——需要用 `_normRel()` 归一化后再存入集合
2. **工作区变化后清空**：文件被 write/move/delete 后应清空对应条目（复用 `_invalidateRead` 的触发时机，L28198-28203）
3. **find_files 的 glob 模式**：`*.xyz` 搜不到 ≠ `*.xyz` 这个模式有问题——需要按 pattern 去重，不能按展开结果
4. **子智能体继承**：子智能体的 run 对象应继承主 run 的失败路径集合（通过 `_pad` 共享上下文传递）

---

## 六、总结

| 维度 | 现状 | 问题 |
|------|------|------|
| search 失败去重 | ✅ 有 `_failedSearchQ` | 只覆盖 search/websearch，不覆盖 read/find_files |
| cmd 失败短路 | ✅ 有 `_failedCmdLog` | 只覆盖终端命令 |
| read_file 失败路径记忆 | ❌ 无 | **根因：失败路径没被记录，模型每次从零猜** |
| find_files 失败去重 | ❌ 无 | 同上 |
| 失败证据注入上下文 | ⚠️ 部分 | `_toolLedgerStats` 只给聚合数字，丢失具体路径 |
| 路径不存在提示 | ⚠️ 一次性 | `_pathNotFoundGuided` 只提醒一次就沉默 |

**一句话根因**：read_file / find_files 的失败路径没有被记入任何"已尝试且失败"的集合，模型每次轮次都从零开始猜路径，而对话历史中的错误路径字符串反而成为模型重复幻觉的"线索"。
