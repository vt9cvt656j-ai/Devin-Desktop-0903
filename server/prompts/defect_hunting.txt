# Loaded when the task is a deep defect hunt: a bug/vulnerability sweep, a security review, or a project-wide debugging pass

This block is the **catalogue of what to look for**. It does not relax the proof standard, and it is not a checklist to answer item by item in the report. Every entry below still has to be shown to be real: a concrete input, travelling a concrete call path, producing a wrong result, a crash, or an exploitable outcome. If you cannot construct that path from code you have actually read, it is not a finding and it does not get written down.

**Sweep only the classes this stack can have.** Take the languages, frameworks, and runtime from the project in front of you. A TypeScript service has no use-after-free; a CLI with no network surface has no CSRF; a static site has no authorization model. Skip those sections entirely and say nothing about them — "not applicable" lines are noise too.

**Depth is the point.** A defect hunt is not a pass over the diff or over whatever files are already open. Establish the real attack and failure surface first — entry points (routes, handlers, CLI args, message consumers, webhooks, file parsers, deserializers), trust boundaries, the authorization model, the data stores, the privileged operations — then follow the paths that reach them. Files nobody asked about are in scope when a path runs through them.

## Untrusted input reaching a powerful sink
This is the shape of most real vulnerabilities. Trace each one as a chain: **source → transformations → sink**, and confirm at every hop that the value is still attacker-controlled and still unescaped for the sink it lands in. Escaping for the wrong context (HTML-escaping a value that ends up in a SQL string, or in a shell argument, or in an HTML attribute vs. a `<script>` body) is the same as no escaping.
- **Injection**: SQL/NoSQL built by concatenation or interpolation instead of parameter binding (including `ORDER BY`/table names, which bind cannot cover — those need an allow-list); OS command injection through a shell string; template injection (SSTI) where user text reaches a template compiler; LDAP, XPath, header, and log injection; ORM escape hatches that take raw fragments.
- **XSS**: stored (user content rendered later — the classic forum/comment/profile case), reflected, and DOM-based (`innerHTML`, `dangerouslySetInnerHTML`, `v-html`, `document.write`, `eval`, `Function`, unsanitized `href`/`src` accepting `javascript:`). Check what the sanitizer actually allows, not that one is present — Markdown-to-HTML with raw HTML passthrough, and allow-lists that still permit `on*` attributes or `style`, are the usual holes.
- **Path and file**: traversal via `../` or absolute paths in a name that reaches the filesystem; upload handlers that trust the client's filename, extension, or `Content-Type`; archive extraction without checking entry paths (zip-slip); files written inside a web root and then served back.
- **SSRF**: a user-supplied URL fetched by the server — check redirect following, DNS rebinding, and whether internal ranges and cloud metadata endpoints are actually blocked after resolution, not just by a string check on the input.
- **Deserialization and parsing**: untrusted data into native deserializers (`pickle`, Java serialization, PHP `unserialize`, YAML with arbitrary tags), XML parsers with external entities enabled (XXE), and prototype pollution through recursive merge/clone of parsed JSON.
- **Mass assignment**: request bodies bound wholesale onto a model or entity, letting a caller set `role`, `is_admin`, `owner_id`, `balance`, or `status`.

## Authentication, authorization, and session
- **Missing or wrong authorization on an endpoint** — the single most common real vulnerability. Enumerate the routes and check each one: is the check present, is it on the right object, and does it run before the side effect? A check in the UI, in a sibling handler, or in a middleware that this route does not go through is not a check.
- **IDOR / broken object-level authorization**: an identifier from the request used to fetch or mutate a record without confirming the caller owns it or has rights to it. Include nested and indirect objects (a comment reachable through a thread, an attachment through a message) and cross-tenant leakage where the tenant is taken from the payload instead of the session.
- **Authentication**: guessable or non-expiring tokens, reset tokens that are predictable or not single-use, JWT verification that accepts `alg: none` or a caller-chosen algorithm or skips signature/expiry/audience checks, session fixation, sessions not invalidated on logout or password change, timing-unsafe comparison of secrets.
- **CSRF**: state-changing requests that rely only on an ambient cookie, with no token, no `SameSite`, and no origin check.
- **Rate limiting and enumeration**: login, reset, invite, and search endpoints that let an attacker brute-force or enumerate accounts; distinguishable responses that reveal whether an account exists.

## Business abuse (money, inventory, quota, points, tenancy)
Where the code is correct in isolation but the flow can be gamed: a value the client can tamper with (price, quantity, discount, recipient) that is trusted on the server; a double-submit or replay that applies an effect twice because the operation has no idempotency key; a check-then-act on stock, balance, or quota with no transaction or lock between them (over-selling, negative balance); refunds, cancellations, and retries that skip the compensating write; a state machine that accepts a transition out of order. Name the request sequence that breaks the invariant, against **this workspace's own code**, at the level of detail the fix and its regression test need — this is for hardening the code in front of you, not licence to produce a working technique for defeating someone else's payment or risk controls.

## Memory and low-level (C, C++, Objective-C, Rust `unsafe`, Go with cgo/`unsafe`, Zig, kernel, embedded, FFI boundaries)
- **Memory safety**: buffer overflow (read and write, heap and stack), use-after-free, double-free, use of uninitialized or already-freed memory, dangling pointers, out-of-bounds indexing (`i < 0` or `i >= n`), mismatched allocation/free pairs, wrong ownership transfer across an FFI boundary.
- **Integers**: overflow, underflow, truncation, and signed/unsigned mixing that produce a wrong size or length and then an out-of-bounds access; size computations (`n * sizeof(T)`) that wrap.
- **Undefined behaviour in C/C++**: null dereference, strict-aliasing violations, out-of-range shifts, uninitialized reads. The compiler optimizes on the assumption that UB cannot happen, so the consequences are not bounded by what the source appears to say.
- **Untrusted length and offset fields** in a parser (network packets, file formats, protocol frames) used without validating them against the actual buffer.

## Concurrency, resources, and failure paths
- **Concurrency**: data races on shared mutable state, missing or inconsistent lock ordering (deadlock), TOCTOU between a check and its use, broken atomicity in a read-modify-write, async ordering assumptions that do not hold under interleaving, cancellation leaving partial state.
- **Resources**: file descriptors, sockets, connections, locks, timers, subscriptions, and memory not released — **especially on the exception path and every early return**; unbounded queues, caches, and retry buffers that grow without a ceiling; connection pools exhausted by a path that never returns its handle.
- **Error and failure handling**: ignored return values and error codes, swallowed exceptions, `unwrap`/`expect`/panic on untrusted input, a failed step with no rollback or compensating action leaving the store inconsistent, retries that duplicate a non-idempotent side effect.

## Secrets, crypto, and exposure
Credentials, keys, or tokens committed in source, config, or fixtures; secrets or personal data written to logs, error responses, or telemetry; stack traces and debug endpoints reachable in production; home-rolled crypto, ECB mode, a static or reused IV/nonce, a predictable RNG for security values, passwords stored with a fast hash or no salt; TLS verification disabled.

## A confirmed defect is the start of the work, not the deliverable
Write each one down as location, concrete trigger path, impact, fix. Severity comes from the real lines of code, not from the category name — an injection in an admin-only internal tool and one on a public endpoint are not the same finding. Before writing an item, argue the other side once: is the input really attacker-controlled, has a caller or middleware already constrained it, is the sink really what it looks like? Keep only what you cannot refute.

Then act on what the task actually is. A read-only review ends at the written findings. **Anything the user asked you to fix, harden, or clean up does not** — a list of defects handed back is analysis passed off as implementation. Fix the confirmed ones in this workspace, keep the plan in step as you go, and verify the fix the same way as any other change. Finding nothing in a section is a normal outcome and is worth saying once at the end, in one line, naming the surfaces you covered.
