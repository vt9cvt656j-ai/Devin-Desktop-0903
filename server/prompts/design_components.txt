# michael-design component layer: tokens, primitives, icons, typography

- Decide the stack and foundation in this order: a stack the user explicitly specified wins; an existing working website keeps its actual framework, language, build tool, styling approach, component library, directory conventions, and utility functions; only an empty workspace, a project with no website, or an explicit rebuild with no reusable or declared stack defaults to React + Tailwind CSS + shadcn/ui (with Vite + TypeScript when the default scaffold needs filling in). Never mix a second framework or component library into an existing website.
- Use the project's existing token carrier and naming; only when there is none do you establish semantic roles such as background/foreground/card/popover/primary/secondary/muted/accent/destructive/border/input/ring/radius. Business components consume only the current project's semantic tokens or semantic classes — never loose colour values. The default Tailwind branch may use CSS-first `@theme inline`, add shadcn/ui primitives as needed, and merge className with `cn() = twMerge(clsx(...))`; other stacks express the same semantics through their native theming API, CSS variables, preprocessor variables, or component system — do not force-port Tailwind classes or a React directory structure onto them.
- "Official primitive" means the component library the project has already adopted; only on the default branch does it mean shadcn/ui + Radix, which is **installed, not imitated**: `npx shadcn@latest init`, then `npx shadcn@latest add <only what this page uses>`. A hand-written "shadcn-style" Button/Card/Input is a defect — it misses focus-visible, disabled, keyboard reach and Radix overlay behaviour, which is what makes a page look homemade. Where primitives exist, compose them. Bring in form, display, navigation and overlay pieces as needed; never install the whole set.
- Button's default/secondary/outline/ghost/link/destructive variants all need hover, focus-visible, active, and disabled — and the same requirement applies to every genuinely interactive control.
- For icons, first map "business concept → object/action/state → icon name", then pick a consistent style from the project's existing icon library or via iconify_search; the default branch may use Lucide. The semantics must match (AI = Bot/Cpu, security = ShieldCheck, analytics = Chart); Sparkles/Wand mean actual sparkle or magic only. Do not use bitmaps, emoji, or ad-hoc hand-written SVG in buttons and toolbars.
- An existing website keeps its font loading method, font families, and type scale unless the user asks for typography to be redone. With no existing system, use a highly readable body font with a system-ui fallback, and choose a display face that matches the michael-design blueprint and category retrieved this round — actually loading it. You may build a 12/14/16/20/24/30/36 size ladder, with body line-height around 1.5, a measure of at most 70 characters, and tabular-nums for figures.
- When the user needs directions to compare, produce only two or three token previews differing in primary/radius/font — do not generate several unfounded AI mockups guessing at styles.
