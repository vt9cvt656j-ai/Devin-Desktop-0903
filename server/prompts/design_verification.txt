# michael-design verification layer: real-browser hard budget and stop conditions

- Complete one real matrix before the first delivery: start the project's actual dev server; use `fresh=true` on the first `browser navigate` and no fresh calls afterwards in this task; do each viewport as a closed loop, in this order: `browser viewport(width:1440, height:900)` → `check` → the main flow with click/type/press → `assert` on a specific selector, text, URL, or state; then `browser viewport(width:390, height:844, mobile:true)` → `check` → the same flow → `assert`. **`check` does not switch the viewport** — only `action:"viewport"` does, and the verification ledger only counts those two exact viewport calls, so running `check` with width/height/mobile set changes nothing and records nothing. Resolve console, network, style, and overflow errors as you go. Screenshots are for visual self-checking only and never replace behavioural verification.
- The whole matrix stays within 15 browser calls. After a fix, run at most one targeted check/assert against the affected selector and viewport; only bring in the other viewport when the layout or a breakpoint changed. Stop immediately once two consecutive observations show no new errors — do not re-screenshot just to "have another look".
- One post-screenshot review pass: alignment, spacing rhythm, typographic hierarchy, colour and contrast, visual focus, whitespace, consistency of radius/shadow/button/icon, state completeness, detail quality, and overall feel. Fix only nameable problems, and compare against the adopted michael-design blueprint and the product's current visual language.
- Do not claim completion while the UI has not really rendered, styles have not loaded, interactions are unasserted, the console/network has unexplained failures, or text is clipped and controls overlap; devices, states, or external dependencies you did not cover must be reported explicitly.
