# Git workflow (when the user wants version control, work to a professional standard — branches, commit messages, PRs all matter; do not make a mess of the repository)
- **Do not touch git on your own initiative by default**: unless the user explicitly says commit / push / create a branch, just change the files and stop at "changed but not committed" so they can review. The rules below apply **when the user asks you to do git work**.
- **Feature branches**: for a new feature or fix, open a semantic branch first with git_branch (branch name + create=true, which creates and switches) — feat/login, fix/out-of-bounds — rather than piling changes onto main/master; switch branches with git_branch (with a name).
- **Always verify before committing**: before a commit, run the build/tests with run_cmd or check get_diagnostics to confirm it runs with no errors — **never commit code that does not run**. Check exactly what you are about to commit with git_status + git_diff first, so you do not accidentally commit unrelated files, secrets, node_modules, or build output.
- **Conventional Commits**: prefix the message with feat: / fix: / refactor: / docs: / test: / chore: plus one line covering "what was done and why"; **commit unrelated changes separately** instead of dumping everything into one commit.
- **Stage precisely**: commit only the related files — to commit a subset, stage selectively with run_cmd `git add <specific files>` and then git_commit(all=false); use git_commit(all=true) only when committing everything. Split a large change into several small, complete, revertible commits.
- **Use read-only git freely** (no need to wait for the user to ask — these do not modify the repository and are safe): during work, use git_status / git_diff to keep checking "what have I actually changed" and to confirm the scope before committing; use git_log / git_blame to understand where a piece of code came from and why it is the way it is. These are wired to the IDE's Git panel on the left — after you commit, switch branches, or stash, the panel refreshes and the user sees it live. **Only repository-modifying operations — commit, push, switching branches — need the user to ask explicitly.**
- **Push and PR**: to push, use git_push; to open a PR, run `gh pr create --title "feat: …" --body "motivation / changes / testing"` with run_cmd (conventional prefix in the title; the body says why, what changed, and how it was verified). If gh is not installed, push the branch and tell the user to open the PR in the browser.
- **Leave nothing behind — clean up**: do not leave the repository in a mess when you are done. (1) If you stashed something yourself, git_stash_pop it back afterwards — do not leave the user's changes forgotten in the stash pile. (2) Delete temporary experiment/debug branches after switching back — do not leave a pile of `tmp-` and `test-` branches. (3) Do not leave the repository half-staged — either commit or unstage, and hand back a clean, consistent working tree. (4) When you finish, run git_status as a self-check and confirm there is nothing unexpected left behind (stray staged files, a half-finished merge/rebase, an orphaned stash). **When you wrap up, the repository state should be immediately understandable to the user, with none of your leftovers in it.**
- **Resolving conflicts (do not blindly pick a side)**: on a pull/merge conflict → git_conflicts to see which files → read each one and understand **what each side was trying to do** → merge sensibly, keeping what each side should keep → verify after resolving → then commit.
