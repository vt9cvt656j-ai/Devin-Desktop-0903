# 做「产品 UI / 官网 / 界面」——先定设计体系，再一次搭对，别对着截图反复磨、别生成图猜风格

用户让你**设计 / 做界面 / 页面 / 产品 UI / 官网**时看这份，配合 `shadcn_design_system`（真实令牌+组件目录+接线）和 `css_concrete_tokens`（令牌契约）一起用。**最高原则：先想清楚做成什么样、定一套语义令牌体系、一次搭对——不是一边写一边疯狂截图试错，更不是先出三张 AI mockup 让人挑。**

**铁律·体系永远在场：写任何网站/页面——不管 React/Vue/Svelte/纯 HTML、不管落地页/官网/工具页/引导页/单文件 demo——设计一律基于 shadcn/ui 语义组件体系 + Tailwind 调色板与 OKLCH 语义令牌。颜色只允许来自语义令牌或 Tailwind 色阶（zinc/slate/blue/emerald…的具体档位），圆角/阴影/间距/字阶全部走令牌；绝不允许随手 hex、随手内联样式、"这次页面小就不用体系了"。框架不支持 shadcn 官方包时按下面第 3 条的映射方案把体系搬过去，而不是放弃体系。**

## ⓪ 先判断力度（别一刀切）
- **从零做完整产品界面 / 官网 / 应用 / 落地页 / 整体重设计** → 走下面「设计体系优先」全流程。
- **往已有项目加一块 / 改个样式 / 做单个组件 / 用户只是问"这块怎么设计"** → **别摆方案选择器、别新起脚手架**：读项目现有栈和设计 token，跟着做那一小块；用户只是问就正面给建议 + 必要时做出来看。
- **已有项目一律跟随它的技术栈和设计系统**（先读 package.json / 样式入口 / 组件目录）；从范围和现有代码能判断是整套还是小改就直接做，只有两种理解会造成实质不同交付时才问。

## 设计体系优先：读懂产品 → 定令牌 → 组合 primitive → 真机验证
1. **读懂真实产品（只读真实存在的，绝不猜）**：先 list_dir 一次看目录**真实内容**——**read 只允许用于列目录结果里出现过的路径**，绝不凭习惯猜 package.json / README.md 去读（猜的路径必然 cannot stat，纯浪费步骤），也**绝不跑出当前工作区**去别的目录翻资料。**空目录 / 全新项目 = 没有事实可读，一次 list 确认为空后立即停止一切探索**，直接凭用户描述 + 你的专业判断进入第 2 步定令牌开干；产品事实（名字/卖点/调性）从用户的话里来，不够就在开干后用界面文案自然呈现或一次 ask_user 问关键取舍。目录**有**真实源码/文案时才去读，读完要说得出这个产品 3 条具体、别处不通用的事实（真功能名/真卖点/真品牌调性），抓住产品**自己的**视觉调性。
2. **定设计令牌体系（这是核心设计动作，取代"猜风格")**：按 `shadcn_design_system` 那套——① 选 base 中性灰阶定冷暖气质；② 定 `--primary` + `--radius` + 标题字体（这三样承担品牌辨识度的 90%，别默认 Inter）；③ 语义色微调并保 WCAG AA。一次改这几个语义令牌，全站自动统一。**颜色一律走语义名，业务里绝不散落 `bg-[#xxxxxx]` / `text-gray-500`。**
   - **已有明确品牌 / 用户已说要什么样** → 直接把它落成一套令牌开干。
   - **需要用户在几个明显不同方向里拍板** → 做 2-3 套**只有 primary/radius/字体不同**的令牌，用 preview_choices 实时渲染让他选（真组件真配色，能动能看）。**别用 generate_image 出三张 mockup 图让人猜**——那是最后不得已、用户明确要"先看张效果图"时才用的可选项，不是定调性的默认方法。
   - **整站/新界面先吃透同类成熟项目**：动手前用 github_trending/仓库搜索/web_search 找 2-3 个同类高星项目（同品类官网/落地页/仪表盘的开源实现），读它们的信息架构、组件拆分、令牌组织和交互细节——高手怎么搭先看明白，再定自己的方案；顺手搜这套栈的全网坑（Tailwind v4 迁移断裂、shadcn 版本兼容、SSR 水合陷阱等），把结论落进计划。
   - **要参考就抓真实数据，别凭印象猜**：需要对标某站、或要从一流产品提取真实设计语言时——**主动用 browser 打开真站点抓真东西**，别脑补：`browser design` 抓它的设计系统（配色/字阶/间距/圆角/阴影/动效 keyframes 的真实数值），`browser inspect` 抓某元素的 computed 样式，`browser nodes` 抓页面真实结构/组件层级，`browser network` 抓它加载的接口/数据/资源，需要页面正文/接口原文用 web_fetch / http_request。**这些是你的抓取能力，该抓就抓——凭印象配色猜间距做出来的界面必然很素很丑。** 抓到的真实数值转成你自己的令牌与布局（学设计语言做原创版本，不照搬受版权保护的文案/图片/独有素材）。需求和体系已明确时直接实现，不做固定数量的参考搜索。
3. **用官方 primitive 组合实现**：已有框架和组件库就沿用。**框架选择铁律：用户没点名框架 → 一律 React+Vite+TS+Tailwind v4+shadcn/ui，不要问、不要用别的**。用户点名了别的框架，同一套设计体系照样搬过去，绝不因为不是 React 就退化成随手内联样式：
   - **Vue/Nuxt** → shadcn-vue + Tailwind v4：OKLCH 语义令牌原封照搬（@theme inline 一样用），组件目录与 React 版基本同名（Button/Card/Dialog…），`npx shadcn-vue@latest init/add`；别把 React 版组件混进 Vue 项目。
   - **纯 HTML/静态页** → 体系不变、载体换掉：语义令牌落成 `:root` CSS 变量（--background/--foreground/--primary/--radius…，深色用 `.dark` 覆盖），全部颜色/圆角/阴影引用变量；组件按 shadcn 的结构和状态手写（hover/focus-visible/disabled/加载态一个不少），图标用 lucide 静态 SVG；能上 Tailwind（CDN 或 CLI）就上，不能就写成一套变量驱动的原生 CSS。
   - **Svelte/Angular/其他** → 先找官方级移植（如 shadcn-svelte），没有就按纯 HTML 方案迁移令牌 + 手写语义组件。
   从零整站必然是多文件任务：**动手写之前先 update_plan 列清楚要建哪些文件、每步做什么、怎么验证，再按计划写**——别跳过计划直接怼文件被工程门拦住又反复重试。按当前官方文档 `shadcn init` + 按需 `add` 页面真用到的组件，禁止全量安装。**有 Button/Input/Card 等 primitive 就组合它们，不另造平行基础组件**；导航/hero/内容区块/图表组合按信息架构写清晰业务组件。新文件第一次 write 就给完整可运行内容，绝不先写空骨架/TODO。
4. **验证 = 真实 dev server 上完成关键交互**：起服务 → **首次** browser navigate(fresh=true) 打开实际 URL，**之后同一 dev server 的所有导航/刷新一律不带 fresh**（反复 fresh 会把浏览器关了又开：窗口闪烁、冷启动几秒、丢页面状态，纯属折磨；只有换站点/登录态污染/开始抓包才重新 fresh）→ browser check 处理控制台/网络/溢出错误 → 用 click/type/press 跑关键流程再对具体 selector/文本 assert。**移动端按项目实际判断，不做仪式**：面向公众的网站/官网/落地页/H5 必须 1440×900 与 390×844 两个视口各验一轮；明确桌面场景（内部后台、桌面工具、用户点名只要桌面版）只验桌面并在收尾说明理由。截图只做视觉自检，不替代 check/assert。**裸 HTML/样式未生效 = 前端没完成**：check 报 no-styles-applied、或截图里是默认衬线字体/无布局纯文本流，绝不允许把这一步打勾、绝不允许"后端可用，前端显示问题后续优化"这种话术收尾——界面就是交付物本体，当场修（Tailwind v4 三件套：vite.config 加 @tailwindcss/vite → CSS 入口 @import "tailwindcss" → main 入口 import 该 CSS；改完重启 dev server 再 check）。**复验像人一样**：完整双视口矩阵一个任务只做一遍（首次交付前）；之后每次修补，页面 HMR 已热更——不重开浏览器、不重设没动过的视口，只对受影响的点重跑 check/assert（改了布局/断点才连带验另一视口）。覆盖目标状态就停，不重复刷同一结果。
5. **动效有工艺不生硬**：动画一律优先成熟库（React 用 `motion`/framer-motion 的 whileHover/whileInView/spring/stagger，Vue 用 @vueuse/motion，纯 HTML 用 Motion One / tailwindcss-animate 预设），自写只允许几行的 transform/opacity transition；微交互 150-250ms ease-out、入场 400-600ms 轻位移+透明度、列表 stagger 逐项，禁 linear、禁旋转弹跳、禁长 keyframes，尊重 prefers-reduced-motion——生硬的手糊 keyframes 一眼假。
6. **反 AI 味**：多区块有密度层次与节奏（特性网格 / 数据指标 / 案例 / 对比 / FAQ / footer），非对称有呼吸的版式；主色克制只用在 primary 动作/选中/链接；圆角/阴影/图标全套统一；标题展示体 + 正文中性无衬线、数字 tabular-nums；图标用 lucide 等真实库、绝不 emoji；文案写这个产品**具体的**卖点/场景，别"赋能/一站式/高效"空话。

一句话：**判断力度 → 读懂真产品 → 定一套语义令牌体系（base+primary+radius+字体）→ 用官方 primitive 组合 → 真机验证后停。** 生成图 + design_board 只在「用户明确要先看几个方向的效果图再拍板」时作可选方向选择器，绝不代替真实令牌体系，绝不是每次机械摆一遍。
